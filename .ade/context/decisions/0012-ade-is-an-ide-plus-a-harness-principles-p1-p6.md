# 0012: ADE is an IDE plus a harness; new scope must pass principles P1–P6

- Status: Accepted (owner, 2026-10-30), with the product doc `_bmad-output/product-ide-and-harness.md` (approved after three adversarial review rounds; the last, on 5f0e90d, passed with minors, applied at 454528c).
- Context: The owner said, "Seems this is becoming an IDE with a harness." ADE had grown by accretion: terminals and previews, a methodology and gates, a fleet view, an MCP library, a secrets vault, a contracts pack, an Orchestrator tab, a phone remote, and plans in flight for Orgo computers, a CLI library and more MCP servers. No standing rule said which proposals belong in ADE, and the review of the in-flight work found shipped features that fail the bar ADE sets for its users: a plain-text API key (the Orchestrator), unprompted money moves and deletes through shipped MCP entries, and nine `npx`/`uvx` entries whose code changes without a user action. The product doc defines ADE as a desktop IDE for coding agents and a harness for Claude Code, lists the seven jobs it serves (Parallel, Check, Done, Setup, Reach, Attention, Contracts), and sets six principles for new scope.
- Decision: ADE adopts principles P1–P6, the override clause and the known-exceptions list, as stated in §4 of the product doc. The principles, verbatim from the doc:

  **How to apply them.** Every plan answers all six. A principle is N/A only when its trigger is absent: P2 when the plan adds no action in its list, P3 when it handles no secret, P4 when no vendor product is involved. P1, P5 and P6 always apply. "Owner to name" under P5 means the principle is unmet until a project is named.

  1. **P1, a job and a change.** Does it serve a job in §2 through the IDE or the harness, with a change the plan names? For the IDE, the change is a step a person no longer takes to see, check or steer agent work. For the harness, it is an agent action that now prompts or is blocked, more agents able to run at once, or a claim that a command now checks. A plan that names no such change fails.
  2. **P2, nothing risky without the user's action.**
     - Is every action that moves money, deploys, deletes, creates a billable resource, or reads or changes credentials done only on the user's click, or behind a Claude Code prompt that holds in every mode, Continuous included?
     - Is third-party software installed only on the user's click, with the exact command shown before it runs?
     - Not counted as installs: ADE writing its own project files (setup, settings merges), and installing ADE's own plugin.
     - A PreToolUse hook that answers `ask` counts toward "every mode" only after a manual check shows its `ask` prompts under `bypassPermissions`. The Claude Code docs don't say whether it does (CLI plan, C16). Until that check passes, in Continuous mode only ask and deny rules count.
  3. **P3, no secrets in plain text.** Are secret values kept out of files ADE writes, synced state, logs and ADE's own settings, held only in the OS keychain or the vendor's own credential store? Does the plan state who else can read them? Today that is any process in an ADE terminal, through the vault's environment export.
  4. **P4, thin where a vendor does the job.** Where a vendor ships a server, CLI or dashboard, does ADE only find it, wire it in, show its data in ADE's own views, and put rules around it, without building its own copy of the vendor's UI or of a capability the vendor already offers?
  5. **P5, real work needs it.** Can the plan name the ardata, CAIDen, academy or ADE project, or the owner's own use, that needs it now?
  6. **P6, provable and keepable.**
     - (a) Everything ADE writes or decides (files, rules, launch flags) is pinned by an offline test in the verification command. How a vendor tool actually behaves is a named manual check. Under ADR 0009, on the unmerged `docs/claude-md-paths` branch, a manual check gates Done only when the plan says so.
     - (b) Every table of vendor tool names or subcommands is built against a recorded fixture of the vendor's own `--help` output, manifest or tool list, with its version and capture date. A test fails when any subcommand or tool in the fixture is not classified as ask, allow, or knowingly unprompted.
     - (c) A named, recurring story re-captures each fixture every quarter, or sooner when the vendor's release notes add a command. The test in (b) then names whatever is new.

  **Override**, verbatim: "The owner may approve a plan that fails a principle. The plan's "Owner's decisions" records which principle, why and the date, and the exceptions list below gains a line. Neither an agent nor silence can waive a principle."

  **The exceptions list** lives in the product doc, §4, "Known exceptions, shipped or decided". It is the one part of that approved doc that keeps changing: each override, and each shipped failure found later, adds a line there, and a line is removed only when the fix ships. This ADR does not copy the list, so there is one list.

  **Scope.** The principles bind plans for ADE itself, in this repository. They are ADE's product principles, not part of the methodology ADE installs: projects that ADE sets up are not bound by them, so nothing in ADE's product templates (`src/lib/projectMethodology.ts`, the vendored ade-setup files) changes.
- Consequences:
  - **Every plan from now on includes a "Principles check" section** answering P1–P6 in turn, each with its verdict and the evidence for it (the job and the change for P1, the actions and their prompts for P2, where secrets live and who can read them for P3, and so on), and N/A only under the trigger rule above. A plan without the section, or with an unmet principle and no recorded override, is not ready for approval.
  - **The adversarial reviewer tests the Principles check** as part of every plan review: it checks each answer against the plan's own design and the code, and a wrong or missing answer is a material finding that blocks.
  - Plans approved before 2026-10-30 are not re-reviewed; the product doc's §6 is their check. A plan not yet approved on that date adds the section before it is approved.
  - Until the plan format carries the section (the product doc's queue has that follow-up: this repo's plans need it, and the change must stay out of ADE's product templates), the plan's author adds it by hand. The vendored `bmad-build` plan template is not edited, because a BMAD update overwrites it.
  - Some shipped features fail today and are listed as exceptions, not waived: the vault's terminal export (P3), the Orchestrator's plain-text key (P3, fix approved), the nine unpinned `npx`/`uvx` MCP entries (P2, pinning queued), shipped MCP entries that move money, deploy or delete without a prompt (P2, audit queued), and the phone remote's own relay (P4, overridden 2026-10-14).
  - Some proposals now wait for a named project (P5 "owner to name") or are deferred (Orgo's native panel, on P4). That is the intended cost: new scope is narrower and slower to approve, and each "yes" says what it changes.
  - P2 and P6(b) make every vendor command table carry a recorded fixture and an unclassified-command test, plus a quarterly re-capture story. That is recurring work the queue must carry.
