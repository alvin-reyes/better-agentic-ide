# 0023: In an engagement, Claude Code starts with a split home, so its cache and logs stay in the profile

- **Status:** Accepted (2026-11-08). Approved by the owner on 2026-11-08 with the F1 plan; accepted on 2026-11-08, when the delta review of revisions 5 to 5g of the F1 design passed. The owner chose option A of design item O1 on 2026-11-08, with option C (asking Anthropic for a cache-folder variable) in parallel and the residual below written into PRD G3 and R3 (`docs/superpowers/specs/2026-11-08-personas-and-engagements-design.md`, sections 8 and 18).
- **Revisions:** 2026-11-08 first version; revision 3 the same day after the re-review (NB3, M-b, M-e); revision 4 after the next re-review (B1, B2, M1, M2, M5); revision 5 (M-D, M-E, minors 2 to 6); revision 5a (the walk's cut point, budget and "could not check" retry); revision 5b (the walk's retry order and back-off, the delete pass's total limit, a hung listing, and delete naming unchecked folders by path).
- **Context:**
  - Claude Code writes per-project MCP and error log folders, named from the Claude Code process's current folder at each write, a subfolder giving its own name (so from client names; design E7.6), to `~/Library/Caches/claude-cli-nodejs/` (macOS) and `%LOCALAPPDATA%\claude-cli-nodejs\Cache\` (Windows). G3 forbids engagement data there. On Linux `XDG_CACHE_HOME`, set per engagement, moves them.
  - Claude Code 2.1.319 has no variable for this folder. It comes from the bundled `env-paths` package, which reads `HOME` (macOS) or `LOCALAPPDATA` (Windows) once at load. Claude Code applies its settings' `env` block afterwards, to itself and every child.
  - Measured on macOS (design E7.3, without signing in): with `HOME` pointing into a fake home and the settings `env` restoring the real `HOME`, the MCP log landed under the fake home, the real cache was unchanged, and the MCP server saw the real `HOME`. The Keychain was unreachable under a bare fake home and reachable once `Library/Keychains` was linked.
  - A sweep of the shared folder was rejected: the client's path is in a shared folder name for the whole session, and a test that only looks after quit would pass while the leak happens.
- **Decision:**
  - `<profile root>/shim/` holds `claude` (macOS: a symlink to the bundled `ade-hook`) or `claude.exe` (Windows: a hard link, or a copy across volumes), prepended to `PATH` in every terminal of the engagement, after the shell's start-up files.
  - `ade-hook` gains an argv0 mode `claude`: it finds the next `claude`, skipping its own folder **during the lookup only**, and passes `PATH` on unchanged, so nested Claude Code started by name goes through the shim too. It sets `HOME=<root>/claude-home` (macOS) or `LOCALAPPDATA=<root>\claude-local` (Windows) and `DISABLE_AUTOUPDATER=1`, and no marker variable. It `exec`s the target on macOS. On Windows it registers a console handler routine that returns TRUE for Ctrl+C and Ctrl+Break (never `SetConsoleCtrlHandler(NULL, TRUE)`, whose ignore flag children inherit), so the target and its children keep normal Ctrl+C handling; it runs the target in a `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` job, waits and returns its exit code; a `claude.cmd` target whose arguments cannot be quoted safely is refused with a message.
  - `<root>/claude-home/Library/Keychains` is a symlink to the real folder (macOS). No ADE walk or delete follows it.
  - A's `<root>/claude/settings.json` carries `"env": {"HOME": "<real home>"}` (macOS) or `{"LOCALAPPDATA": "<real>"}` (Windows), maintained with ADE's other entries (ADR 0019).
  - A's session-start hook checks its own Claude Code process, never an inherited variable: on macOS the process's start-time `HOME` (`KERN_PROCARGS2`) must be `<root>/claude-home`; on Windows the shim (`<root>\shim\claude.exe`) must be an ancestor with no other Claude Code between, with process names matched ignoring `.exe` and ASCII case on Windows. On a mismatch, or when it finds no Claude Code process, it warns in the session, the journal and A's tab; it never passes by default.
  - A's instance runs a leak detector, at start and every 60 s, and the delete flow runs it once: it lists the cache folder an unshimmed Claude Code would use, keeps in memory only names equal to the slug of A's root or a checkout or starting with that slug's first 200 characters and `-` (Claude Code's slug rule, cut and hash included, with the hash's absolute value taken unsigned as JavaScript does, design E7.6), keeps a longer name only if **the guided walk** (design section 8: a no-follow walk inside that root or checkout that descends only into directories matching the rest of the name and, below the 200-character cut of a long name, examines the whole subtree below the cut point, including a cut that lands inside a folder name, with no depth cap but a budget of directories and time) finds the subfolder it names, and drops every other name unseen. Each kept name is walked once per run of A (a keyed hash of it is remembered, never the name). A folder the walk cannot list, a budget hit, or a listing call that hangs past the budget (each listing runs on a blocking thread under a timeout, abandoned when it hangs) gives "could not check", never "no leak"; such a name is shown and walked again, round-robin with the oldest attempt first and, after a budget hit, a per-name back-off doubling to a cap of 32 passes, so it is not part of the unseen residual. The delete flow's pass is limited to 300 s in all; it removes the matched folders and names each unchecked one by its path in delete's report, kept. `.git`, `node_modules` and `target` are walked last, never skipped. Paths are absolute (Windows long paths work) and compared case-insensitively on Windows; junctions are links. On a hit it warns and offers to delete those folders with the no-follow helper.
  - The detector's real-Claude test (macOS and Windows) is part of the verification gate, not advisory.
  - The isolation test runs a nested `claude mcp list` on macOS and Windows, bounded by 10 s MCP connect and start-up timeouts, a 60 s kill of the nested run and a 180 s step limit: a `.mcp.json` wrapper server approved through `enabledMcpjsonServers` in A's user settings (by the harness only; ADE's own code never writes that key or `enableAllProjectMcpServers`), which nests exactly once (a variable and a create-new guard file) from a subfolder, and an assert that the nested level's `mcp-logs-<marker>srv` exists under A's split home for that subfolder's slug, so a vacuous run is red.
- **Consequences:**
  - Claude Code's cache, MCP and error logs stay in A's profile for every Claude Code started by name in A, nested ones included, and for ADE's own launches.
  - **Residual** (the same as design section 8, "What it cannot see", and PRD G3 and R3): a Claude Code started in A by absolute path, under a `PATH` reset, or through the Agent SDK, that runs no session hook, still writes client-named folders to the shared cache. It is detected, after the write, only when its current folder was A's root, a checkout or a folder inside one, while A runs or at delete. Not detected: (i) a current folder outside A's root and checkouts; (ii) a subfolder created, used and removed between two passes, or while A is not running; (iii) a name whose folder was gone when the guided walk first checked it and which later gains one again in the same run of A, until A's next start. G3 does not hold for it; the owner had G3 and R3 name it (design O1, P7).
  - It depends on Claude Code reading its cache folder at load. The isolation test runs a pinned real Claude Code (`claude mcp add`, `claude mcp list`, no account) and RC-2 the current one, so a change in that order is caught.
  - A `claude` started by absolute path, or by a wrapper that resets `PATH`, bypasses the shim. With a session-start hook it is warned by the per-process check; without one (`claude mcp ...`, an SDK process without user settings) only the leak detector sees it, after the write, and only under A's folders. Detected, not prevented.
  - Claude Code's own auto-update is off inside engagements; the engineer updates it from a default-profile terminal.
  - Windows and a signed-in macOS session are unmeasured until the isolation test's Windows run and the session check (design appendix B, steps 6 and 8).
  - When Anthropic offers a variable for this folder (design O1 option C), it replaces the shim.
