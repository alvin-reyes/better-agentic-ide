# 0003: Agent status reaches ADE through a command hook, a bundled helper and a loopback endpoint

- Status: Proposed (2026-10-14). Records decisions from the owner-approved spec `docs/superpowers/specs/2026-10-14-agent-status-design.md`, as built for piece 1. The contract is `.ade/context/agent-events.md`.
- Context: ADE has to know, per terminal pane, when a Claude Code agent is working, waiting or blocked on a prompt, and phone pieces 2 and 3 need the same states. Claude Code reports these only through hooks written into a project's settings. Those files outlive ADE and are read by sessions started outside it, so whatever ADE writes has to be harmless there. It also has to work with two ADE processes running at once (the installed app and a dev build) and must not make `cargo test` or `tauri dev` depend on a build step that a fresh checkout doesn't have. In the spikes against 2.1.299, `http` hooks never delivered `SessionStart`, didn't expand a port taken from the environment, and printed a hook error on every prompt whenever nothing was listening.
- Decision:
  - **A command hook, not an `http` hook.** Every ADE entry is `{ "type": "command", "command": "\"${ADE_HOOK_BIN:-true}\"", "timeout": 5 }`, with no matcher, for ten events. It is written to `.claude/settings.local.json` only when the user turns Agent status on, and only ADE's own entries are removed when it goes off. Outside ADE the variable is unset, so the hook runs `true`. The quotes keep a path with a space (`Better Terminal.app`) whole. ADE never returns hook decisions.
  - **A separate helper crate.** The helper is `src-tauri/ade-hook`, a member of a Cargo workspace rooted at `src-tauri`. Its logic is one file, `src-tauri/src/hook_forward.rs`, which the main crate also compiles, so the existing `cargo test` covers it. It is bundled only through `tauri.release.conf.json` (`externalBin`); the release workflow builds it and copies it in before `tauri build`. `tauri dev` and `cargo test` never reference it. At run time ADE looks for it beside its own executable.
  - **A loopback endpoint with a per-launch token.** ADE listens on `127.0.0.1` on a free port picked at each launch. It puts `ADE_HOOK_BIN`, `ADE_HOOK_PORT`, `ADE_HOOK_TOKEN` (random, new each launch) and `ADE_PTY_ID` into each terminal, after first removing any inherited values. It refuses a wrong token, any `Origin`, a foreign `Host`, a method other than POST, and a body over 16 KB, and it always answers `{}`. If the endpoint can't bind, or the helper is missing, none of the four variables is set.
- Consequences:
  - Each ADE process reports only to its own endpoint, and ADE never rewrites project files when it starts. Sessions already running pick the hooks up from their next prompt.
  - A fresh checkout's checks need no extra step. A dev build needs `cargo build -p ade-hook` before Agent status works there, and says so when the helper is missing.
  - **Forgeable status, which piece 2 must settle.** The token is in the environment of everything started in an ADE terminal, so any of it can post events. That is acceptable for a status dot. Piece 2 must not let a phone approve a `PermissionRequest` on the strength of this token alone, and it has to settle that before it holds requests.
  - A long-lived process started in an ADE terminal, such as a tmux server, keeps stale variables after that ADE quits. Its sessions then report to a port nobody holds; the helper fails quietly. If the helper's path has gone, those sessions show a hook error until they are restarted.
  - Windows shows no toggle until the hook command is checked on Claude Code's Windows shell.
