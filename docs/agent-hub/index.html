Agent Hub Guide

How to make, run and configure an agent hub: a private repo of Bash and Markdown that holds the context, state and history of one technical persona's work for one client, on Claude Code. Every session starts with what is live, open and waiting. The agents keep it up to date. The client's code stays in its own repos.

What a hub is

A hub is one private Git repo per client and role. Its CLAUDE.md makes Claude Code the persona you picked, such as a DevOps/SRE, a staff engineer or a fractional CTO, and its folders hold the state of each work area. Hooks print that state when a session starts and tell each terminal what the others changed. When a folder session ends, they journal its commits and commit its notes. Scheduled jobs push the hub, run your monitors and write a morning briefing.

Context

The persona, the shared rules, and each folder's CLAUDE.md and ACCESS.md (names and locations, never values).

State

Each folder's STATE.md: Live, Staged, Open, Waiting on, Next session starts with.

History

journal/<UTC date>.md, the append-only timeline every agent and hook writes to, plus memory/.

Recall

bin/brain: every Markdown section in a local SQLite index, searched by keyword and by meaning.

Requirements

The scripts target macOS and Bash 3.2 or later. They use launchd, the Keychain (security), notifications and Terminal or iTerm through osascript, and BSD stat and date.

From template to first session.

  1. Create the repo from the template and clone it. 
    gh repo create my-acme-sre --private --template alvin-reyes/ai-agent-hub-template --clone
cd my-acme-sre

    Without GitHub: run bin/init … --dest ~/Project/acme-sre from a template checkout. It copies the template to that new folder first, leaving out .git, hub.conf, repos/ and _bmad-output/. The folder must not exist yet. Add a private remote there (git remote add origin <url>). Without an origin, sync commits but never pushes, and still logs synced.

  2. Pick a persona and initialize. 
    bin/init --list                                   # the personas
bin/init --persona devops-sre --client "Acme Corp" --owner "Sam Lee" \
  --repo acme/infra=~/code/infra --remote deploy@staging.acme.com:22 --remote-key ~/.ssh/acme \
  --staging-url https://staging.acme.com --secret grafana-token --briefing 08:00

    --persona, --client and --owner are required. bin/init never overwrites a hub that already has a hub.conf, and it writes no secrets.

  3. Commit and push the hub once, by hand. 
    git add -A && git commit -m "Initialize the hub" && git push -u origin main

    bin/init commits nothing, and bin/sync's path list leaves out hub.conf. Without this commit, a fresh clone has no hub.conf: its hub name falls back to the folder name, which changes the state folder, launchd labels and Keychain service, and it has no secret names to check. Pushing with -u also sets the upstream that auto sync needs before it can scan commits ahead of a push. Commit hub.conf by hand again whenever you edit it.

  4. Link it into Claude and check what this Mac can reach. 
    bin/setup                          # memory + skills links, git hooks
ollama pull nomic-embed-text       # once per Mac, optional
bin/brain index
bin/doctor                         # OK / MISSING per tool, login, repo, box, secret
bin/secret --set grafana-token     # hidden prompt; never an argument
  5. Turn on the scheduled jobs. 
    bin/schedule install               # weekday briefing, monitor + sync every 30 min
  6. Start working. 
    claude                             # at the hub root: the main agent (use your --claude wrapper if you set one)
bin/work ops/environments          # deep work in one folder's repo, in a new Terminal

Add a persona

Copy a file in personas/. Keep its front matter and use {{CLIENT}} and {{OWNER}} in the body, then write the persona's habits:

---
title: DevOps / Site Reliability Engineer
folders: ops/environments ops/ci-cd ops/monitoring ops/security
model: sonnet
briefing_focus: Report failing checks, expiring certificates, backups not verified, and cost changes.
---

## Who you are

You are the **DevOps / Site Reliability Engineer** for {{CLIENT}}, working for {{OWNER}}. …

briefing_focus is added to the morning briefing's prompt. model becomes the hub's default session model.

A folder's files

FileHolds
CLAUDE.mdTwo lines on what the work is, plus folder rules: code changes only in this folder's repos, on a branch, as a draft PR; update STATE and the journal at the end. It imports @ACCESS.md, @memory/MEMORY.md and @STATE.md.
ACCESS.mdCode table (Repo · Checkout · Default branch · Who merges · CI), Machines, Services, Credentials (locations only), Permissions and Undo (live change → rollback command). The Code table's Checkout column is what bin/work, bin/setup and the hooks read.
STATE.mdUpdated: then Live, Staged, Open, Waiting on, Next session starts with. bin/context prints the first lines of Live, Open, Waiting on and Next session.
memory/One fact per file with a description: in its front matter, indexed in MEMORY.md. Never secrets, phone numbers or contact email addresses.

Make a new work area with bin/new projects/<name> or bin/new ops/<name>. It never overwrites existing files (it prints kept), and it runs bin/setup to link the new folder's memory.

A day in the hub. Hub commits come from the main agent, bin/sync, and a folder session's end (that folder and the journal only). Code is committed only in the client repos.

  • Main agent (a session at the hub root, started with the hub's Claude install) reads the state and proposes tasks. On your go, it spawns each folder's named agent with the task, not the history. It never does a folder's work without reading that folder's CLAUDE.md, ACCESS.md and STATE.md first.
  • Folder agents (projects/app → app, ops/ci-cd → ops-ci-cd) work only in their folder's repos. They stage production changes for you and end with five lines or fewer.
  • The persona agent handles work that spans folders or needs judgement: planning, trade-offs, proposals, client emails, reviews and deploy decisions.
  • Several terminals can run at once. The UserPromptSubmit hook tells each one what the others changed since its last prompt.

Hooks

The hub root's hooks are in .claude/settings.json. Each folder's hooks are in <folder>/.claude/settings.json, made from templates/folder-settings.json. bin/work passes that file with --settings, because a deep-work session runs in the client's checkout, outside the hub.

bin/changes keeps one snapshot per session in ~/.agent-hub/<name>/changes-seen.<session_id>. The first prompt only records a baseline. Output is capped at 40 lines, journal text is trimmed to 200 characters, and snapshots older than 7 days are removed.

  • Remote Control is on for every session, named after the folder (projects/acme → acme), so you can follow it from your phone. --no-remote turns it off. Use that with API-key wrappers such as OpenRouter or Ollama, because Remote Control needs a claude.ai login.
  • --prompt "<task>" sends the session's first message.
  • Specialist agents. Markdown agent files in <folder>/.claude/agents/ (front matter name, description, optional tools and model) are passed to the session as --agents. bin/new doesn't create any; add them yourself. HUB_AGENT_MODEL is their default model. --agent-model sonnet or --agent-effort high sets all of them, and --agent-model reviewer=opus sets one; the named value wins. With no specialist agents, these options exit with "has no specialist agents". The folder's named agent in the hub's .claude/agents/ is for the main agent at the hub root, not for bin/work.

  • WORK_DRY=1 prints the command without opening a window. AGENT_TERMINAL=iterm uses iTerm.

The brain: searchable memory

bin/brain keeps every Markdown and text section of the hub in one SQLite file, .local/brain.db. That covers STATE, memory, the journal, notes, docs and the paths in HUB_BRAIN_PATHS. The file is gitignored, and there is one per hub, so clients never mix. Files stay the source of truth, and the index is rebuilt from them.

ollama pull nomic-embed-text                               # once per Mac
bin/brain index                                            # incremental; --full rebuilds
bin/brain search "what did the client decide about SMS"    # file:line, heading, snippet
bin/brain search -n 15 --json "cert expiry"
bin/brain status                                           # files, sections, embedded, stale, model, db

Auto sync

bin/sync commits and pushes hub files only: README.md CLAUDE.md ACCESS.md memory journal reports projects ops docs bin templates tests .claude .githooks .github .gitignore .bigfiles-allow launchd .ade _bmad _bmad-output llms.txt. It never commits repos/ or other staged files.

ModeDoes
bin/syncReview only: lists pending changes and a diff stat, and notes untracked files under .claude/ that --yes would include.
bin/sync --yesCommits sync <date> <time> (through the pre-commit hook) and pushes.
bin/sync --autoThe same, unattended, with the safeguards below. It runs every 30 minutes and at each folder session's end. Exit 0 means synced, nothing to do or skipped. Exit 1 means refused or failed.

Each run writes one line to ~/.agent-hub/<name>/logs/sync.log. To turn auto sync off, set HUB_AUTO_SYNC=0 in hub.conf (or run bin/init --auto-sync off on a new hub), then run bin/schedule install again. That removes the sync job, and session end stops pushing.

The secret scan of commits about to be pushed runs only when the branch has an upstream. That's why the first push is done by hand with -u. Paths in the list that don't exist are skipped.

The morning briefing

bin/briefing runs the hub's Claude install with -p on the briefing model (Haiku by default). It can only use Read, Grep, Glob, bin/context and bin/brain search. It writes a briefing of 25 lines or fewer covering five things: what's live and healthy, anything broken, what's waiting on you, the client or others, upcoming calls and deadlines, and the top five tasks with their folders. It adds the persona's briefing_focus. The briefing goes to the journal, and a notification says "Morning briefing is in the journal". A failure is journaled as "briefing failed". MONITOR_QUIET=1 silences the briefing's notification as well as the monitors'.

Monitors

A monitor is any executable projects/<x>/monitors.d/*.sh or ops/<x>/monitors.d/*.sh. It must be read-only. The first line of its output is its status, and any line starting with ALERT raises an alert.

#!/bin/bash
# ops/environments/monitors.d/staging.sh
code=$(curl -s -o /dev/null -m 10 -w '%{http_code}' https://staging.example.com/health)
echo "$(date -u '+%a %H:%M UTC') | staging health $code"
[ "$code" = 200 ] || echo "ALERT staging health returned $code"

A leading timestamp such as Fri 10:05 UTC | or 2026-10-30 10:05Z | is ignored when comparing statuses, so a new time alone doesn't count as a change. An alert is journaled once and clears when a run has no ALERT line. State is kept in ~/.agent-hub/<name>/monitor-state/.

hub.conf

bin/init writes this file and every script sources it. It holds names and locations only, never secrets. Commit it by hand after each edit, because bin/sync doesn't include it.

Which edits take effect

  • Read on every run: the Claude install and config dir, HUB_MODEL and HUB_EFFORT (for bin/work), the briefing model and focus, the remote box, staging URL, secret names, repos, code owner, tools, brain paths, embedding settings and auto sync. Re-run bin/schedule install after changing the briefing time or auto sync, and bin/setup after changing the Claude install or config dir.
  • Written once, at creation: the client, owner, title and persona model go into CLAUDE.md, ACCESS.md, README.md and the persona agent. HUB_AGENT_MODEL goes into each folder agent file when bin/new makes it. The remote box, staging URL and secret names also go into ACCESS.md. Changing those keys later changes nothing in those files, so edit the files too.
  • Don't rename HUB_NAME on a working hub. It moves the state folder and the launchd labels, and the old jobs keep running (run bin/schedule uninstall first). The Keychain service stays the old name unless you also change HUB_KEYCHAIN_SERVICE.

How memory is linked

Claude Code keeps auto-memory per working directory under <config dir>/projects/<encoded path>/memory. bin/setup replaces each of these with a symlink into the hub, so memory is committed and travels with the repo:

  • the hub root → memory/
  • each folder → <folder>/memory/
  • each checkout in a folder's Code table → that folder's memory/. A checkout shared by two folders goes to the first one that claims it, and a folder that has the phrase memory owned by anywhere in its ACCESS.md is processed last, so another folder that lists the same checkout claims it first. Later claimants get a warning.

Existing memory there is copied in first, and the old folder is kept as .bak-<time>. BMAD skills are linked into <config dir>/skills/ unless a skill with that name already exists and isn't the hub's.

Secrets and safety

  • Secrets live in the macOS Keychain under the hub's service name. bin/secret --set <name> reads the value from a hidden prompt. bin/secret <name> prints it for $(…) use only. --has, --forget and --list (names only) do what they say.
  • The pre-commit hook (.githooks/pre-commit) refuses anything under repos/, files over 1 MB (unless listed in .bigfiles-allow) and anything gitleaks flags. If gitleaks isn't installed, the hook only warns and the commit goes through, so install it on every Mac.
  • Auto sync also scans every commit about to be pushed, including ones made with --no-verify, when the branch has an upstream. It never force-pushes.
  • The brain never indexes a section that looks like a key, token, password or private key.
  • Gitignored: repos/, .local/, .env*, *.jsonl, PDFs and images, .claude/settings.local.json.
  • bin/remote runs SSH in batch mode with a 10 s connect timeout. Agents may run read-only commands. Anything that writes needs your word for that change.
  • bin/doctor never prints a secret and always exits 0.

Agent rules

The rendered CLAUDE.md binds every agent in the hub. In short:

  • Verified, not vibed. Work test-first in the client repo. Tests and a live check decide Done, and agents report real output, failures included.
  • Every answer cites a source opened in this session: path:line, a URL, a command's output or a hub file. Without one the answer is "unverified".
  • Code changes go in the client's repos, on a branch, with small commits and tests. They follow each repo's own rules.
  • Commits and PRs carry only the owner's git identity, with no AI attribution.
  • Deploys, writes to shared systems and anything production need the owner's word for that change. Each deploy is verified live and journaled.
  • Client decisions belong to the client and are recorded with who and when. Messages to the client are drafts only.
  • Proposals include a Revenue / cost impact section with numbers, sources and labelled assumptions (templates/proposal.md).
  • Token budget: read on demand, send long output to a file, reuse STATE and the journal, keep replies short.
  • BMAD v6 skills (bmad-prd, bmad-spec, bmad-ticket, bmad-build, bmad-code-review, …) are used for planning and builds. Their output stays in the hub's _bmad-output/, never in the client repo. The ADE rules in .ade/rules.md win over BMAD.

A new Mac or a fresh clone

STATE.md, memory, the journal and ACCESS.md are committed, so a fresh clone starts with full context:

gh repo clone <you>/my-acme-sre && cd my-acme-sre
bin/setup && bin/brain index
bin/doctor                     # shows what this Mac is missing
bin/secret --set <name>        # for each secret doctor lists
bin/schedule install

Secrets, SSH keys and files outside the repo (downloads, PDFs) don't travel. bin/doctor lists what's missing. This works only if hub.conf was committed (see Make a hub).

Clone to the same absolute path. Several committed files hold the first Mac's absolute paths: each folder's .claude/settings.json (the hook commands), HUB_CLAUDE_CONFIG_DIR in hub.conf, and output_folder in _bmad/config.toml. Use the same user name and folder. Otherwise, fix those values: move each folder's .claude/settings.json aside and run bin/new <folder> again, edit hub.conf and _bmad/config.toml, then run bin/setup and bin/schedule install.

Upgrading a hub made before auto sync

  1. Folder sessions only hear about hub changes through the UserPromptSubmit hook, and bin/new keeps an existing folder settings file. For each folder, move <folder>/.claude/settings.json aside and run bin/new <folder> again, or add this line under "hooks": 
    "UserPromptSubmit": [{ "hooks": [{ "type": "command", "command": "\"/path/to/hub\"/bin/changes projects/<x>" }] }],
  2. Run bin/schedule install again to load the monitor and sync jobs.
  3. Auto sync is on unless hub.conf says HUB_AUTO_SYNC=0. It needs gitleaks and bin/setup; without them every run is refused and logged.
