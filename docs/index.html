Orchestration

Orchestrate your developer tooling with a team of agents.

Many agents, each in its own lane and on its own model, working one plan. BMAD v6 decides who does what, the verification command decides when it is done, and an agent hub remembers all of it between sessions.

In ADE

Sub-terminals

Give one terminal tab several shells: New Sub-terminal in the tab’s menu, ⌘[ and ⌘] to switch. Closing one checks whether it is busy first, and they come back with the session. Scrollback never goes into the repo.

Different agents, different models

The right model for each job

The hub sets defaults per persona, and hub.conf or the command line overrides them: one model for focus sessions and the persona agent, one for folder specialists (default Sonnet), and one for the morning briefing (default Haiku).

Agent hub

A hub that remembers each client’s work.

The agent hub template turns a private repo into an AI technical persona for one client: its context, state and history in Bash and Markdown, while the client’s code stays in its own repos. Every session starts with what is live, open and waiting.

Thirteen personas

Pick a role, run bin/init

Staff engineer, DevOps/SRE, data, ML/AI, mobile, frontend, QA, security, solutions architect, tech lead, engineering manager, technical PM or fractional CTO. bin/init writes the hub for one client and owner.

Focus terminals

One terminal per work area

bin/work <folder> opens the folder’s code checkout with its named agent, hooks and model. --model and --agent-model set the session and its specialists per run.

State, memory, journal

Nothing lives only in a chat

Each folder keeps STATE.md (live, open, waiting on, next) and memory/; the journal is the shared timeline. Hooks show every terminal what the others changed since its last prompt.

The brain

One brain for every agent

All of the hub’s work lives in one SQLite brain: STATE, memory, the journal and notes, plus any other folders you point it at with --brain-path. Every agent is told to run bin/brain search before it asks or re-derives, so each one starts with the context of the whole hub. FTS5 keywords plus vectors from a local Ollama model; nothing leaves the Mac.

Auto sync

Pushed, and scanned first

bin/sync --auto commits and pushes the hub every 30 minutes and at each session end: refused without gitleaks, every commit scanned before the push, one rebase retry, never a force push.

Monitors and briefing

Watching while you’re away

launchd runs read-only monitors every 30 minutes (an ALERT line journals once and notifies) and a weekday morning briefing on Haiku.

Access

Reach the box, keep the secrets

bin/remote for SSH to the client’s box, bin/secret for the macOS Keychain (names in the repo, never values), and bin/doctor for what this Mac can reach.

02

Built for serious software engineering work

An agent will tell you it is finished. The question is who checks. ADE sets every project up with a methodology that answers that, and roles that cannot mark their own homework.

Anthropic’s SDLC is the methodology. BMAD is the framework. Both are baked into ADE.

The root of all of it

BMAD, in every project and actually used

Not a nod to a methodology. The pinned BMAD-METHOD v6 goes into every project ADE opens: 33 skills in .claude/skills/, its config in _bmad/ and tickets in _bmad-output/. No Python or uv for setup, tickets and the core workflows: those skills call a bundled Node script. v6 dropped BMAD’s QA gate, so ADE keeps its own, one verdict per ticket in .ade/gates/. Nothing is downloaded and nothing you already have is overwritten.

The roles name the skills that do their job, so the Scrum Master runs the ticket tree with bmad-ticket and QA reviews with bmad-code-review before it records the verdict, instead of improvising both. BMAD’s two phases, Planning and Dev cycle, are the phases ADE shows you, because they are the ones the work is actually in.

BMAD v4 is still a choice for a new project: the classic .bmad-core/ with 21 tasks, 13 templates, 6 workflows, 6 checklists and 6 reference sets, plus 21 /BMad:tasks: commands for Claude Code. A project already on v4 stays on v4 until you switch it: the first time you open one from the New tab dialog, ADE asks once whether to keep v4 or switch to v6.

Switching is one dialog, in either direction. It lists every path that would move before anything does. Nothing is deleted: the old version goes to .ade/archive/ inside the project, with a journal of what moved, and your documents in docs/ stay where they are unless you tick them. If a step fails, ADE puts everything back.

Done is a command, not an opinion

Every project agrees one verification command up front. A story is Done when it passes on that commit, with the output shown. Not when an agent says so.

No agent certifies its own work

The Developer writes the failing test first, then the code. QA judges the result and may not edit code or tests, because a verifier that repairs what it measures can make its own verdict come true.

An adversarial reviewer that cannot patch

It ships with a read-only tool allowlist on purpose: Read, Grep, Glob, Bash. It judges and reports. Widening it to unblock a story is how review stops meaning anything.

Nineteen roles, each with boundaries

Analyst through security engineer, SRE and release manager. Each one states what it owns, what it must not touch, and whose job the rest is, so parallel agents stop contradicting each other.

What they learn stays in your repo

A knowledge store per role, committed with the project. Shared contracts go to the context store where parallel agents read them. An update never overwrites either.

How an agent is composed

A prompt that says “you are a senior engineer” is a costume. An agent here is two things joined: a role that fixes what it is accountable for, and a domain that narrows what it is working on. The role is the part that holds.

Role 19

What it is accountable for, the artifacts it owns, and what it must not touch. QA may not edit the code it judges. The adversarial reviewer ships with a read-only tool allowlist.

×
Domain 44

One technical focus: Backend API, Database, CSS, Containers, CI/CD, Solidity. It narrows what the agent knows. It never widens what the agent may do.

=
Agent 47

Named pairings, ready to launch. Developer × Backend API is the API Builder; Developer × Database is the Database Engineer. Same accountability, different ground.

The role’s definition is handed to the provider verbatim, not rebuilt from parsed fields, because it carries sections ADE does not model and a recomposition would silently drop them. The domain is appended as a Focus section underneath. Boundaries survive the pairing by construction, not by convention.

Execution

Where each one acts

Roles are not decoration. Each step of the flow has an owner, and the handoff between them is the point: the agent that builds is never the agent that signs it off.

  1. Plan

    The product manager writes the PRD. The architect writes the architecture and names the one verification command. The designer writes the UX spec, DevOps the ops plan.

  2. Approve

    The adversarial reviewer attacks each artifact first, defaulting to block on any material flaw. Then you approve. A reviewer that waves things through defeats the point.

  3. Shard

    The scrum master splits the plan into small, independently testable stories, so several agents can work without colliding.

  4. Build

    Developer agents take one story each, test first. They run in parallel because each role states what it owns, so two agents do not quietly edit the same artifact.

  5. Verify

    QA or you run the verification command on that commit, with the output shown. A story is Done when it passes. Not when an agent says so.

FAQ

Questions, answered

Is it really free?

Yes. Download ADE; nothing is locked.

How does licensing work?

It does not. ADE is MIT licensed: no keys, no accounts, no seats to count. Use it at work, fork it, ship your own build.

Which agents does it support?

Any CLI agent runs here, but ADE is built around Claude Code and goes deepest with it: sub-agents in .claude/agents/, a CLAUDE.md constitution, sub-agent lanes on the fleet timeline, and real spend read from its transcripts. Codex and Ollama run side by side and show no cost, because they publish none.

How many agents can run at once?

As many as your machine and your provider's rate limits allow. Ten is what we test.

Does it store my keys?

API keys stay in your OS keychain, never synced. ADE never handles private keys.

Which platforms does it run on?

macOS (Apple Silicon and Intel) and Linux (.deb or AppImage). Or install from the terminal with curl -fsSL https://ade.ardata.tech/install.sh | bash, which picks the right build for your machine. Windows support is coming soon.
