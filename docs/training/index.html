Learn ADE and the agent hub by doing

Two short, hands-on tracks. Each step has the exact command or click and what you should see. Shortcuts show macOS first, then Linux.

Track 1 · ADEInstall, set up a project, plan → approve → shard → build → verify, sub-terminals, the stage board. Track 2 · Agent hubMake a hub, the first session, focus terminals, the brain, the journal, auto sync and the briefing.
Track 1 · about 15 minutes

ADE: one project, from plan to a verified story

You need macOS or Linux, git, and Claude Code (npm install -g @anthropic-ai/claude-code).

  1. Install ADE

    curl -fsSL https://ade.ardata.tech/install.sh | bash

    It picks the build for your machine, checks it against the release's SHA256SUMS and installs without sudo. Run it again later to upgrade. You can also use the download page.

    You should seeADE in /Applications on macOS, or the AppImage in ~/.local/bin on Linux.

  2. Make a tiny practice project

    mkdir -p ~/Project/hello-ade && cd ~/Project/hello-ade && git init

    Launch ADE. It opens with one terminal in your home folder and a short tour. Then cd ~/Project/hello-ade in that terminal.

    You should seethe file browser and fleet view follow the terminal into hello-ade.

  3. Let project setup run

    The first time a terminal enters a project ADE has no record of, it sets it up for agents, adding only files that are missing. Opened from the New tab dialog, it first asks BMAD v6 (default) or BMAD v4; set up any other way, it gets v6. You can also run Project: Set up BMAD, methodology and agents from the command palette (⌘P / Ctrl+Shift+P).

    You should seea toast, then .claude/agents/ with eight roles (product manager, architect, designer, scrum master, developer, QA, DevOps, adversarial reviewer), BMAD v6 skills in .claude/skills/, _bmad/, and the rules in .ade/rules.md, loaded from CLAUDE.md.

  4. Start an agent

    Type claude, or press ⌘⇧A / Ctrl+Alt+Shift+A for the agent picker. For longer prompts, open the scratchpad with ⌘J / Ctrl+Shift+J and send with ⌘↵ / Ctrl+Enter.

    You should seeClaude Code running in the project, with the eight roles available as sub-agents.

  5. Plan: ask the planning roles

    The work flows in five steps:

    Plan→Approve→Shard→Build→Verify

    Ask by name, for example:

    Use the product-manager agent to write a PRD for a CLI that adds two numbers.
Then use the architect agent to write the architecture, with one verification command.
    You should seedocs/prd.md and docs/architecture.md, which names the one verification command (for example npm test) under "Verification command". On v6, BMAD skills write their documents under _bmad-output/; where the two differ, the BMAD location is the one to use.

  6. Approve, after the skeptic

    Have the adversarial-reviewer look at the PRD and the architecture.

    Fix what it blocks on, then approve the plan yourself. Approval fixes the verification command; changing it later needs your approval again.

    You should seea review with findings by severity, and after you approve, a dated line in the journal .ade/session.md.

  7. Shard into stories

    Use the scrum-master agent to shard the plan into stories.
    You should seesmall, independently testable stories in docs/stories/, one file each, and a journal line per story.

  8. Build one story, test-first

    Use the developer agent to build story 1, test-first.

    The developer writes the failing test, then the code, runs the verification command and reports its real output. It does not mark the story Done. Several developers can run in parallel, each in its own git worktree.

    You should seea new test, the code, and the command's output in the agent's report.

  9. Verify: the only path to Done

    Use the qa agent to verify story 1.
    You should seethe real output recorded in the story's Verification section and a journal line. A story is Done only when the verification command passes; no agent certifies its own work.

  10. Watch it on the stage board

    Open it with ⌘⇧Y / Ctrl+Alt+Shift+Y (View: Toggle stage board). On a v6 project it maps BMAD's four phases (Analysis, Planning, Implementation, Validation) and refreshes as agents write files. You can Approve a draft and Dispatch an approved story to a developer agent in a new tab.

    You should seeyour documents listed by phase; a story that says it is done without a passing QA gate shows as claimed.

  11. Run a side shell with a sub-terminal

    Right-click the tab and choose New Sub-terminal. Switch between a tab's sub-terminals with ⌘[ and ⌘] (Ctrl+Shift+[ and Ctrl+Shift+] on Linux). Closing one that is still running something asks first.

    You should seea second shell in the same tab and folder, for a test watcher or a dev server beside the agent.

Check yourself

  • Where do the eight role agents live, and what file holds the rules? (.claude/agents/, .ade/rules.md)
  • Which document names the verification command, and who can change it? (docs/architecture.md; only with your approval)
  • Who marks a story Done? (Nobody by assertion: only a passing verification command, recorded by QA or you.)
  • How do you open the stage board and switch sub-terminals?

Track 2 · about 15 minutes

Agent hub: a persona that remembers one client's work

The ai-agent-hub-template is private for now; this track assumes you have access. You need macOS, git, gh, Claude Code, and gitleaks for auto sync. Ollama is optional.

  1. Pick a persona

    gh repo create my-acme-sre --private --template alvin-reyes/ai-agent-hub-template --clone
cd my-acme-sre
bin/init --list
    You should seethe personas: staff software engineer, DevOps/SRE, data, ML/AI, frontend, mobile, QA, security, solutions architect, tech lead, engineering manager, technical product manager, fractional CTO.

  2. Make the hub

    bin/init --persona devops-sre --client "Acme Corp" --owner "Sam Lee" \
  --repo acme/infra=~/code/infra --briefing 08:00

    Without GitHub, add --dest ~/Project/acme-sre to copy the template to a new folder first.

    You should seehub.conf (names and locations, never secrets), the persona in CLAUDE.md, and one folder per work area, such as ops/environments.

  3. Commit hub.conf once, by hand

    git add -A && git commit -m "Initialize the hub" && git push -u origin main

    bin/init commits nothing and bin/sync leaves hub.conf out, so this is the one commit you make yourself. push -u also sets the upstream auto sync needs.

    You should seethe hub on GitHub, with hub.conf in it.

  4. Link it to Claude, and check this Mac

    bin/setup && bin/doctor
    You should seeOK or MISSING per tool, login, repo, box and secret name. bin/doctor never prints a secret.

  5. First session in the hub

    claude
    You should seethe session start with what is live, open and waiting, from each folder's STATE.md.

  6. Open a focus terminal

    bin/work ops/environments
bin/work --model opus --prompt "Check the last pipeline run" ops/ci-cd

    Each folder opens in its own Terminal, in the folder's repo checkout, with its named agent and hooks. --model sets the session's model; --agent-model sets the folder's specialist agents.

    You should seea new Terminal window. Other terminals hear what it changed on their next prompt.

  7. Search the brain

    ollama pull nomic-embed-text     # once per Mac, optional
bin/brain index
bin/brain search "what did the client decide about SMS"
    You should seefile, line, heading and a snippet for each match: SQLite keywords plus local Ollama vectors, on this Mac only. Without Ollama it still works, keyword only.

  8. Write to the journal

    bin/journal ops/environments "Rotated the staging certificate"
    You should seea dated entry in journal/<UTC date>.md, the timeline every agent and hook shares.

  9. Sync, with the secret scan

    bin/sync           # review first
bin/sync --yes     # commit and push the hub's files

    Auto sync (bin/sync --auto) also runs at every focus session's end. It refuses to run without gitleaks, scans every commit to push, retries a rejected push once with a rebase, and never force-pushes or touches the client's code.

    You should seethe hub's changes pushed. Auto sync logs one line per run in ~/.agent-hub/<name>/logs/sync.log.

  10. Turn on the scheduled jobs

    bin/schedule install
bin/schedule status
    You should seethree launchd jobs: the weekday morning briefing (read-only, on Haiku, into the journal and a notification), bin/monitor every 30 minutes, and bin/sync --auto every 30 minutes.

Check yourself

  • Which file must you commit by hand, and why? (hub.conf; nothing else commits it)
  • How do you open a focus terminal on one folder with a different model?
  • Where does the brain live, and does it ever leave the Mac? (.local/brain.db, gitignored; no)
  • What does auto sync refuse to do? (Run without gitleaks, force-push, or push the client's code)
